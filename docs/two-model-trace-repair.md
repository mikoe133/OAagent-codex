# 两模型 Trace 失败诊断与修复

后续准确性与速度优化已完成并重载本地 Agent，当前状态见
[报告准确性与速度优化](grounded-report-optimization.md)。下文验证数字和部署状态为本阶段历史记录。

分析对象：2026-09-30 两份“所有员工的八月进度概览，除了实习员工”对话导出。
不保存员工正文、姓名或连接凭据；脱敏回放结果在
`artifacts/trace-optimization/two-model-replay.json`。

## 已确认的原因

| 模型 | 用时 | 命令数 | 失败数 | 失败分布 |
| --- | ---: | ---: | ---: | --- |
| GLM 5.3 | 434.542 秒 | 30 | 14 | 6 次 neq，4 次 report.id，3 次元数据暂停，1 次 rg 无匹配 |
| DeepSeek V4 Flash | 443.362 秒 | 12 | 2 | batch 子查询多了 id；字段中使用 LEFT(...) |

GLM 的 `neq` 与服务端原有 `ne` 不一致；模型改了日期、关联和排序仍保留错误
操作符。报表 ID 如 `2026-08-...`、`syntax-check` 只是追踪标签，却被错误套用
SQL 别名规则，导致继续重试。DeepSeek 的查询 ID 同样不参与 SQL，但原协议
不接受；`LEFT(...)` 则确实违反结构化字段引用规范，应该使用 `textLength`。

原错误响应只有“查询参数不符合结构化查询规范”，没有路径、允许值和恢复方式。
因此模型难以定位问题，转向读源码、移除期间等无效尝试。GLM 的命令总耗时
约 9.442 秒，DeepSeek 约 1.976 秒；对话总耗时不能归因于数据库执行慢，
其余耗时包含模型生成、推理、传输和编排，不能仅凭 Trace 进一步精确分摊。

GLM 07:33:46 开始收到 `metadata_validation_failed`，又查询 catalog、sleep
后重试。07:38:15 本地检查状态为 unchanged，版本与两份 Trace 相同。旧同步
catch 会丢弃底层异常并把连接/检查失败统一标记为定义校验失败；它没有保留该次
失败快照。因此无法确定当时具体是哪个连接或文件错误，不能断言真实字段变更。

## 修复

- 在结构化协议中兼容完全等价的 `neq` → `ne`，不改变筛选值、对象或期间。
- `query.id` 可选并回显；`report.id` 使用独立的普通标签规则（1–128 字符）。
  SQL 别名、字段、实体、关联和权限继续严格校验，不开放原始 SQL 表达式。
- query/batch/report 共用 schema 校验，返回具体 `issues.path`、允许值及修正
  提示。正文函数错误会提示 `textOffset/textLength`。不回显业务筛选值。
- 提示模型只修错误参数，保留业务条件；错误重复时停止，避免扫描服务源码。
  数据库模式直接关联周历并按区间相交查询，消除“必须先用日期接口查编号”的冲突。
- 后台同步只对明确的临时数据库错误额外重连一次，不增加正常请求的调用次数。
  持续临时失败进入 30 秒起的后台退避，最多退至原同步间隔；对话不轮询等待。
- 区分 `metadata_sync_unavailable` 和 `metadata_validation_failed`。两者在未验证
  恢复前均停止读取，不以旧快照绕过校验。失败阶段/错误码记录到日志和
  `last-failure.json`，成功恢复后仍保留最后失败诊断，不记录原始驱动异常或凭据。
- 已生成 report 后若后续读取失败，回答仅补充简短范围说明，不再拼接大段对象
  正文；成功刷新 report 后恢复对象覆盖检查。正文预览按实际 textLength 标记
  可能截断，避免不足 6000 字的预览被误认为完整内容。

所有改动都作用于通用工具协议、错误恢复和范围标记；没有姓名、月份、员工类型
或自然语言意图关键词分支，没有增加模型审核调用。
